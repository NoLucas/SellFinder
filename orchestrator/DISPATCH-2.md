# DISPATCH-2 — 2차 사이클 설계

2026-08-16 · 계약 `v0.2.2` · 1차 사이클 종료(DISPATCH.md §6 4개 조건 PASS) 이후

> 1차의 목표는 **"지도가 실제로 칠해지는가"** 였다. 달성했다.
> 2차의 목표는 하나다 — **"예측이 실제로 생성되는가."**

---

## 0. 지금 비어 있는 것

1차가 끝난 지금도 **이 제품은 아직 예측을 만들지 못한다.**

| 사실 | 근거 |
|---|---|
| B 의 모델은 동작한다 | `predict_batch` (`intelligence/scoring/model.py:266`), 백테스트·모델카드 완비 |
| C 의 API 는 예측을 **만들지 않는다** | 라우트가 GET 3개 + dev 토큰뿐. **`POST /predictions` 자체가 없다** |
| C 가 내보내는 점수는 **가짜다** | `prediction_store._build_demo_regions()` 하드코딩 |
| B 와 C 사이에 연결이 **하나도 없다** | `intelligence` 를 import 하는 코드가 `backend` 에 0건 |

**즉 1차에서 우리가 검증한 것은 "가짜 점수가 지도까지 정확히 도달하는가" 였다.**
경로는 맞았다. 이제 그 경로에 진짜를 흘려보낸다.

## 1. 이번 사이클의 최대 위험 — 이음매가 VF-003 과 같은 모양이다

B↔C 는 지금 **두 에이전트가 각자 맞는데 붙이면 안 맞을 수 있는** 전형적 자리다.
VF-003 이 정확히 그랬고, 세 폴더가 전부 초록불인 채로 지도가 비어 있었다.

그래서 이번엔 **이음매 테스트를 나중이 아니라 먼저 만든다.**
`predict_batch` 를 C 의 잡 워커를 통해 실제로 호출하고, 그 결과가 `/scores` 응답 형태로
나오는 것까지 한 번에 실행하는 테스트가 **C-2 착수 조건**이다.

> 원칙: **이음매는 만든 사람이 아니라 이음매 자체가 테스트를 가진다.**

## 2. 의존 순서

```
B-1 진입점 공개 ──────► C-1 POST /predictions 골격 ──► C-2 잡 워커가 B 호출 ──┐
                                                                              ├─► D-1 상세 패널
A-1 sbiz 택소노미 매핑 ─────────────────────────────► B-2 실피처 기반 예측 ──┘
검증-1 evidence 규칙(§6) 추적 ← C-2 가 들어온 뒤에야 검증 가능
```

**임계 경로는 B-1 → C-1 → C-2 다.** A 와 D 는 그 사이 병렬로 자기 몫을 진행한다.

## 8. 종료 조건

넷이 **동시에** 참이면 2차 사이클이 끝난 것이다.

1. `POST /predictions` 가 202 + `run_id` 를 반환하고, 그 run 의 `/scores` 가 **B 가 계산한 값**을 준다
2. `backend` 에 `_build_demo_regions()` 가 **존재하지 않는다**
3. B↔C 이음매 테스트가 두 폴더 중 **어느 쪽 스위트에서든 실행**되고 통과한다
4. 검증이 evidence 규칙(§6) 4개 조항에 대해 **구멍이 아닌 판정**을 낸다

## 9. 1차에서 배운 것을 이번에 적용한다

- **이음매 테스트를 먼저.** 1차에서는 통합 테스트가 없어 VF-003 이 검증 회차까지 살아남았다.
- **자기 폴더 밖에 쓰지 않는다.** 완료 보고는 자기 `RECONCILIATION.md` 에 남긴다.
  총괄자 폴더에 직접 쓰지 마라 (`c5deeb0` 사례).
- **막히면 조건을 스스로 확인한다.** "총괄자가 알려줄 때까지 대기" 를 만들지 않는다.
  각 항목의 착수 조건은 파일 존재나 명령 출력처럼 **에이전트가 직접 확인 가능한 형태**로 준다.
- **값을 지어내지 않는다.** 1차의 VF-004·VF-011 은 전부 "모르는 값을 그럴듯하게 채운" 것이었다.
  모르면 503 이나 null 이나 질문이지, 추측이 아니다.
