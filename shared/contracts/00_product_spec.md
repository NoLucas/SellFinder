# 00. SellFinder 제품 스펙 (v0.2.0 · Enterprise)

> 이 문서가 흔들리면 나머지 전부가 흔들립니다. 코드를 쓰기 전에 반드시 읽으세요.

---

## 1. 한 문장 정의

**SellFinder는 기업이 자사 제품을 등록하면, 한국 전역의 지역별 소비 데이터를 기반으로
"이 제품을 어느 지역에서 어떤 채널로 팔 때 얼마나 팔릴지"를 금액과 근거와 함께 예측해
지도 위에서 의사결정할 수 있게 하는 B2B SaaS다.**

핵심 단어 세 개를 놓치지 마세요.

- **자사 제품(SKU)** — 일반 카테고리가 아니라 사용자가 등록한 구체적인 제품이 예측 단위다.
- **금액과 근거** — 0~100 점수만으로는 기업이 움직이지 않는다. 예상 매출액과 왜 그런지가 필요하다.
- **채널** — 같은 제품도 편의점이냐 자사몰이냐에 따라 지역별 성패가 완전히 달라진다.

---

## 2. 우리가 흔히 잘못 만드는 것 (Anti-goals)

지금 각 에이전트가 서로 다른 걸 만들고 있는 원인이 대부분 여기 있습니다.

| ❌ 이렇게 만들지 마라 | ✅ 이렇게 만들어라 |
|---|---|
| "카페 업종이 잘 되는 지역" 을 보여주는 상권분석 툴 | "우리 회사의 8,000원짜리 콜드브루 SKU"가 잘 팔릴 지역 |
| 단일 테넌트 전제로 DB 설계 | 모든 테이블에 `tenant_id`, 토큰에서 파생 (요청 파라미터 금지) |
| `predicted_score: 87` 하나만 반환 | 예상 매출액 + 신뢰구간 + 요인 분해 + 유사 지역 근거 |
| 지역 = 행정동 하나로 고정 | 시도/시군구/행정동/집계구/H3/사용자 정의 상권 다중 해상도 |
| 예측 API를 동기 호출로 설계 | 전국 3,500개 행정동 × 다수 SKU는 **비동기 잡** |
| 채널 무시 | (제품 × 지역 × **채널** × 기간) 이 예측의 키 |
| 자사 판매 데이터 미고려 | 업로드 시 모델을 테넌트별로 **보정(calibration)** |

## 3. 사용자와 의사결정 (Who decides what)

예측 결과가 어떤 버튼을 누르게 만드는지가 스키마를 결정합니다.

| 페르소나 | 업종 | 내리는 의사결정 | 필요한 출력 단위 |
|---|---|---|---|
| **점포개발 담당** | 프랜차이즈 F&B, 리테일 | 다음 분기 신규 출점 후보 10곳 | 상권(catchment) 단위 예상 월매출 + 기존점 잠식률 |
| **영업/유통 MD** | CPG·제조 | 어느 지역 대리점·체인에 SKU를 밀어넣을지 | 시군구 × 채널 단위 예상 판매량 |
| **카테고리 매니저** | 대형 유통사 | 점포별 SKU 구색·진열 배분 | 점포 단위 SKU 랭킹 |
| **퍼포먼스 마케터** | 이커머스·D2C | 지역 타게팅 광고 예산 배분 | 행정동 단위 수요 밀도 + 예상 ROAS 기여 |
| **물류/SCM** | 이커머스 | 물류센터·재고 전진배치 | 권역 단위 수요 예측량 |

> **설계 함의:** 하나의 점수로 이 다섯을 다 만족시킬 수 없다.
> 예측 요청에 `objective` (출점 / 유통확대 / 광고타게팅 / 재고배치)를 받고,
> objective 별로 랭킹 기준을 다르게 한다. (`05_scoring_spec.md` 참조)

## 4. 핵심 난제 4가지와 우리의 해법

### 4.1 브릿지 문제 — 자사 SKU를 공개 데이터에 어떻게 잇는가

공개 소비 데이터(상권정보, 카드매출 통계)는 **업종** 단위입니다. 사용자가 등록하는 건 **SKU** 입니다.
그 사이를 잇는 게 `02_taxonomy.json` 의 3단 브릿지입니다.

```
[테넌트 SKU]  "제로 슈거 콜드브루 350ml, 3,900원"
      │  ① 속성 추출 + 자동 분류 (모델 A)
      ▼
[상품 택소노미]  식품·음료 > 음료 > 커피 > RTD커피
      │  ② 채널 매핑
      ▼
[유통 채널]  편의점 / 대형마트 / 온라인 오픈마켓 ...
      │  ③ 공개데이터 코드 매핑 (KSIC · 상권정보 업종코드 · 카드 MCC)
      ▼
[지역별 공개 소비 신호]  region × 업종 × 기간 소비액
```

**②③ 매핑은 반드시 계약 파일에 명시적으로 존재해야 한다.** 모델이 즉흥적으로 추론하면 재현이 불가능해집니다.

### 4.2 콜드스타트 — 신규 고객은 자사 데이터가 없다

데이터 성숙도를 3단계(Tier)로 정의하고, **Tier에 따라 예측 방식과 신뢰도 표기를 다르게** 합니다.

| Tier | 고객 상태 | 예측 방식 | 출력 |
|---|---|---|---|
| **T0** | 가입 직후, 자사 데이터 0 | 공개 데이터 기반 카테고리 수요 × 제품 속성 적합도 | 상대 랭킹 점수만. **금액 추정 제공 금지** |
| **T1** | 자사 판매 데이터 일부 지역 업로드 | T0 위에 테넌트 스케일 보정 + 잔차 모델 | 금액 추정 + 넓은 신뢰구간 |
| **T2** | 12개월 이상 × 30개 지역 이상 | 테넌트 전용 모델 학습 | 금액 추정 + 좁은 신뢰구간 + 백테스트 성적 공개 |

> **T0에서 금액을 추정해 보여주는 건 제품 신뢰도를 죽이는 가장 빠른 길입니다.**
> 랭킹은 신뢰할 수 있어도 절대값은 신뢰할 수 없다는 점을 UI가 명확히 말해야 합니다.

### 4.3 시점 정합성 — 미래 정보 누수(leakage)

2024년 매출을 학습하면서 2026년 인구 피처를 쓰면 모델 성적이 실제보다 좋게 나오고,
운영에 올리면 무너집니다. 모든 지역 피처에 `valid_from` / `valid_to` 를 두고,
학습·백테스트 시 **as-of 조회**만 허용합니다. (`03_region_features.json` 참조)

### 4.4 설명 없는 점수는 팔리지 않는다

기업 사용자는 이 예측을 들고 임원 보고에 들어갑니다. "87점"으론 방어가 안 됩니다.
모든 예측은 **승법 요인 모델**로 분해되어, 각 요인이 점수를 얼마나 밀어올리고 끌어내렸는지
기여도와 근거 데이터를 함께 반환합니다. (`05_scoring_spec.md` 참조)

## 6. v1 범위 (Scope) — 여기 없는 건 만들지 마세요

**포함**
- 지역 해상도: 시군구 + 행정동 (집계구·H3는 스키마만 준비, 구현은 v2)
- 채널: 편의점, 대형마트/SSM, 백화점, 전문점/로드샵, 온라인 오픈마켓, 자사몰, 외식매장
- objective: `store_expansion`, `distribution_push`, `ad_targeting`
- 예측 기간: 향후 1~12개월
- 자사 판매데이터 업로드: CSV/XLSX + 스키마 매핑 UI

**제외 (v2 이후)**
- 실시간 예측, 개인 단위 타게팅, 해외 지역, 자동 발주 연동, 경쟁사 SKU 단위 추적

## 7. 성공 기준

| 지표 | 목표 |
|---|---|
| 랭킹 품질 (Spearman ρ, 홀드아웃 지역) | T2 기준 ≥ 0.60 |
| 상위 10% 지역 리프트 | 전체 평균 대비 ≥ 2.0배 |
| 금액 추정 오차 (wMAPE) | T2 기준 ≤ 25% |
| 예측 재현성 | 동일 `run_id` 재실행 시 100% 동일 결과 |
| 전국 행정동 예측 잡 | 단일 SKU 기준 ≤ 90초 |

## 8. 용어 통일 (다르게 부르지 마세요)

| 용어 | 의미 | 금지 표현 |
|---|---|---|
| `tenant` | 고객사 | company, org, client |
| `product` | 테넌트 소유 SKU | item, goods |
| `taxonomy_node` | 공용 카테고리 분류 노드 | category(단독 사용 금지) |
| `region` | 지역 단위 (레벨 명시) | area, zone, district |
| `channel` | 유통 채널 | store_type, sales_type |
| `demand_signal` | 공개/라이선스 소비 데이터 | market_data |
| `tenant_sales` | 테넌트가 업로드한 자사 실적 | sales_history |
| `prediction_run` | 버전 고정된 예측 실행 단위 | job, batch |
| `opportunity_score` | 0~100 정규화 랭킹 점수 | score, predicted_score |
