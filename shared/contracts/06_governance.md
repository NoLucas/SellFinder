## 1. 테넌트 격리 — 가장 치명적인 실패 지점

한 고객사의 판매 데이터가 다른 고객사에게 보이는 사고는 계약 해지와 소송으로 직행합니다.

### 필수 구현

1. **`tenant_id` 는 액세스 토큰에서만 파생한다.**
   쿼리 파라미터, 요청 바디, 헤더 어디로도 받지 않는다. 받으면 `400 TENANT_ID_NOT_ALLOWED`.

2. **행 수준 보안(RLS)을 DB 레벨에서 건다.**
   애플리케이션 코드의 `WHERE tenant_id = ?` 에만 의존하지 않는다. 한 곳만 빠뜨려도 유출된다.

   ```sql
   ALTER TABLE tenant_sales ENABLE ROW LEVEL SECURITY;
   CREATE POLICY tenant_isolation ON tenant_sales
     USING (tenant_id = current_setting('app.current_tenant_id')::text);
   ```

3. **공용 데이터와 테넌트 데이터를 물리적으로 분리한다.**

   | 구분 | 예시 | 저장 위치 |
   |---|---|---|
   | 공용 (전 테넌트 공유) | `region`, `region_feature`, `demand_signal`, `taxonomy_node` | 공용 스키마 |
   | 테넌트 전용 | `product`, `tenant_sales`, `own_store`, `prediction*` | RLS 적용 스키마 |

   `03_region_features.json` 의 `tenant_scoped` 피처(own_store_count_2km 등)를
   실수로 공용 피처스토어에 넣으면 즉시 유출입니다. 이게 가장 흔한 실수입니다.

4. **모델 학습 시 테넌트 데이터 혼입 금지.**
   T2 테넌트 전용 모델은 해당 테넌트 데이터로만 학습한다.
   공용 기저 모델(f₁~f₇)에는 어떤 테넌트의 `tenant_sales` 도 들어가지 않는다.
   교차 학습을 하려면 **명시적 계약상 동의**가 선행되어야 하며, v1 범위에서는 하지 않는다.

5. **캐시 키에 tenant_id 를 포함한다.** 빠뜨리면 캐시를 통해 유출된다.

## 2. 개인정보 (개인정보보호법 · 신용정보법)

### 2.1 원칙
이 제품은 **집계 데이터만** 다룹니다. 개인 단위 데이터는 시스템에 들어와서는 안 됩니다.

### 2.2 인제스트 단계 차단
`tenant_sales` 업로드 시 아래 컬럼이 감지되면 **잡 전체를 거부**하고 사유를 반환한다.

- 고객명, 연락처, 이메일, 주민등록번호 패턴
- 카드번호 패턴 (13~19자리 숫자, Luhn 통과)
- 개별 거래 단위 행 (동일 지역·기간·SKU 에 대해 행 수가 비정상적으로 많은 경우 경고)

거부 메시지 예: `"고객 식별 정보로 보이는 컬럼(phone)이 포함되어 업로드를 중단했습니다. 지역·기간 단위로 집계한 파일을 올려주세요."`

### 2.3 집계 임계값 (k-익명성)
`demand_signal` 의 셀 단위 관측치가 임계 미만이면 원시값을 노출하지 않는다.

- 임계: 셀당 최소 관측 점포 5개 **또는** 거래 50건
- 미달 시 `coverage_flag = 'suppressed'`, 값은 상위 지역 값으로 대체하거나 null
- **suppressed 셀의 원시값은 API 응답, 로그, 내보내기 파일 어디에도 나가면 안 된다**

### 2.4 데이터 소재지
v1 은 국내(KR) 리전 고정. 해외 리전 복제 금지. 백업도 국내.

## 3. 데이터 리니지 · 라이선스

기업 고객은 반드시 "이 숫자 어디서 나온 겁니까"를 묻습니다. `data_source` 테이블이 그 답입니다.

### 필수 규칙
1. **출처 없는 숫자는 인제스트하지 않는다.** `region_feature.source_id` 는 NOT NULL.
2. **`commercial_use_allowed = false` 인 소스는 프로덕션 투입 금지.**
   특히 카드 소비 데이터와 통신사 유동인구는 라이선스 조건을 반드시 확인한다.
   공공누리 유형(제1~4유형)에 따라 상업적 이용 가능 여부가 다르다.
3. **API 응답에 `data_freshness` 를 포함한다.** 어떤 소스가 언제 기준인지 사용자가 알아야 한다.
   상권정보는 분기 갱신이라 최대 3개월 시차가 있고, 이걸 숨기면 나중에 신뢰 문제가 된다.
4. **크롤링 금지.** 공식 API 또는 배포 파일만 사용한다. robots.txt 및 이용약관 준수.

### data_source 등록 예시
```json
{
  "source_id": "src_sbiz_market",
  "name": "소상공인시장진흥공단 상권정보",
  "license": "공공누리 제1유형",
  "commercial_use_allowed": true,
  "refresh_cadence": "quarterly",
  "granularity": "adm_dong / quarterly",
  "known_limitations": ["점포 개폐업 반영에 최대 3개월 시차", "무점포 사업자 미포함"]
}
```

## 4. 감사(audit) · 재현성

예측 결과로 수억 원짜리 출점 결정이 내려집니다. "그때 왜 이렇게 나왔죠?"에 답할 수 있어야 합니다.

### 필수 기록 (`audit_log`)
- 누가(`actor_user_id`) 언제 어떤 예측을(`run_id`) 어떤 파라미터로 실행했는가
- 결과 조회·내보내기 이력
- 권한 변경, 데이터 업로드/삭제

보관 기간 최소 3년. 테넌트 계약 종료 시에도 익명화 후 보존.

### 재현성 3요소
`prediction_run` 은 아래 셋을 고정 기록하며, 셋이 같으면 결과가 **100% 동일**해야 합니다.

1. `params` (난수 시드 포함)
2. `model_version`
3. `feature_as_of` — 이 시점의 피처 스냅샷

> 피처 스토어를 덮어쓰기(upsert)로 갱신하면 과거 예측이 재현 불가능해집니다.
> 반드시 append-only + valid_from/valid_to 방식으로 관리하세요.

## 5. 모델 거버넌스

- 모든 프로덕션 모델은 `model_card` 를 갖는다 (`05_scoring_spec.md` §5.3).
- 모델 교체 시 이전 버전을 최소 90일 유지한다. 진행 중인 의사결정이 있기 때문.
- **드리프트 모니터링**: 주요 피처의 분포와 예측 점수 분포를 월 단위로 추적하고,
  기준 대비 PSI > 0.2 이면 알림.
- 자동 재학습 금지. 재학습은 백테스트 통과 후 사람이 승인한다.

## 6. 보안 기본선

| 항목 | 요구사항 |
|---|---|
| 전송 암호화 | TLS 1.2+ |
| 저장 암호화 | 저장소 암호화 필수, `tenant_sales` 는 추가 컬럼 암호화 권장 |
| 인증 | OAuth2 client credentials (서버간) + SSO/SAML (콘솔) |
| 비밀 관리 | 코드/리포지토리에 자격증명 하드코딩 금지. 시크릿 매니저 사용. |
| 삭제 요청 | 테넌트 데이터 삭제 요청 시 30일 내 파기 + 파기 증명서 발급 |
| 로그 | 로그에 개인정보·자격증명·suppressed 원시값 기록 금지 |

## 7. 사용자에게 반드시 고지할 것 (제품 내 문구)

거버넌스는 문서에만 있으면 소용없고 UI 에 나타나야 합니다.

- 예측은 **추정치**이며 실적을 보증하지 않는다 (특히 T0)
- 각 수치의 **기준 시점**과 **출처**
- 신뢰도 `low` 인 지역은 시각적으로 명확히 구분
- `do_not_use_for` 에 해당하는 사용 시 경고
